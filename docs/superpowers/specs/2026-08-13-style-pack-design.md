# devspace-ai：用例风格包（Style Pack）设计

> 状态：待用户审阅规格  
> 日期：2026-08-13  
> 项目：`devspace-ai`  
> 前置规格：[2026-08-12 用例草稿生成](2026-08-12-devspace-ai-case-generation-design.md)  
> 结论先行：要提升「不同业务 / 不同风格」的生成质量，本轮做**可维护的范文风格包**，**不上 RAG**

## 1. 文档目的

把「生成用例时按选定风格写」固化为可实施设计：在 `devspace-ai` 内维护带范文的风格包，生成时选用。本文是 implementation plan 与验收依据。

一句话理解：

- **风格包 = 带范文的文件夹**（例如「支付接口」「营销活动页」）
- **一组范文 = 一篇对照**：左边是需求片段，右边是我们认为写得好的用例
- 生成时选哪个文件夹，模型就按哪套范文写；不选则与现在完全一样

## 2. 背景与目标

### 2.1 问题

v1 只把**当次需求**和可选的一句话 `domain_hint` 送给模型。不同用户、不同测试系统、不同业务的用例写法差很大，模型不知道「这家」合格用例长什么样，草稿容易泛。

`domain_hint` 现状（本轮不改其语义）：

- 调试页「领域提示」可选输入，随生成请求传到模型
- 拼进 user 消息：需求正文后追加 `Domain hint: …`
- 无密钥时 Fake 模型**忽略**它；真实模型仅把它当口头提醒
- 不入库、无范文、不改 Graph

风格包用具体用例教模型，而不是靠一句话。

### 2.2 为何不是 RAG

「保存需求/用例样板」≠「知识库检索系统」。本轮样板数量小、由人指定用哪一包，不需要切分、向量库、按相似度召回。

库很大、人选不过来时，再把「按包取范文」换成检索实现；检索应发生在明确的语料上，而不是先造知识库产品。

### 2.3 目标

1. 调试站有独立页面：新建 / 编辑 / 删除风格包；**不能保存空包**。
2. 现有生成页增加「用例风格」下拉（可空）；选中后把该包范文注入提示词。
3. 运行轨迹能看出用了哪个包、几组范文。
4. 对外 API 可列出风格包，生成时可带 `style_pack_id`（供以后 TMS 接入）。
5. 不选包时，v1 生成行为不变。

### 2.4 非目标

- 向量检索 / 自动找相似用例
- 登录、权限、多租户隔离（同一环境内所有包可见、可选、可改）
- 从 TMS 自动同步用例进包
- 风格包版本历史
- TMS（`cdp-suite`）内的管理或生成界面
- 新的质检、归因等 Capability
- 独立 SPA

## 3. 已确认决策

| ID | 决策 |
| --- | --- |
| SP-001 | 采用方案 B：样板作为 AI 服务内一等资产，有维护页；生成时点选风格 |
| SP-002 | 不上 RAG；只按用户选定的包注入范文 |
| SP-003 | 维护页与生成页都落在现有 `/debug/`（Jinja + 少量 JS，无登录） |
| SP-004 | 生成时风格包**可选**；不选 = v1 原路径 |
| SP-005 | 创建/保存时必须至少 1 组完整范文；不允许空包 |
| SP-006 | 包有 `id`（UUID，生成时用）和 `key`（稳定代号，创建后不可改） |
| SP-007 | 范文中的用例与生成结果同一套 `CaseDraft` 字段，走同一套领域校验 |
| SP-008 | 每包最多 5 组范文；每包合格用例合计最多 8 条 |
| SP-009 | `domain_hint` 保留；与风格包可同时使用；**写法以范文为准** |
| SP-010 | Fake 模型忽略范文（与忽略 `domain_hint` 一致）；看风格差异需真实模型 |
| SP-011 | 删除为真删；生成时包不存在 → 明确 4xx，不调用模型 |
| SP-012 | 风格包 CRUD 用 JSON API；生成仍为 `multipart/form-data`，增加可选 `style_pack_id` |
| SP-013 | 调试页调用与对外相同的 application 服务，禁止旁路实现 |
| SP-014 | PostgreSQL 持久化：`style_packs` 表 + 范文 JSONB |
| SP-015 | 当次需求文本 + 包内范文合计不超过现有文本上限（默认 50k 字符），超出拒绝 |

## 4. 方案取舍

| 方案 | 要点 | 结论 |
| --- | --- | --- |
| A. 样板由 TMS 每次请求带上 | AI 不养内容，隔离自然 | 不选：当前希望在 AI 侧有可维护、可切换的风格资产 |
| B. AI 内风格包 + 维护页 | 生成时选包 | **采纳** |
| C. 仓库内静态 YAML | 改样板要发版 | 排除：不适合多业务维护 |
| 完整 RAG | 向量检索历史用例 | **排除本轮**；语料大、选不准时再考虑 |

曾考虑「先建空文件夹再贴范文」：已否决。空包会让人以为已经套了风格。创建/保存时就必须有范文；生成下拉里只出现已保存的合法包。

## 5. 领域模型

### 5.1 风格包

| 字段 | 说明 |
| --- | --- |
| `id` | UUID，生成下拉与 API 选用 |
| `key` | 稳定代号，如 `cdp.payment.api`；全局唯一；创建后不可改 |
| `name` | 页面显示名，如「支付接口」 |
| `description` | 可选，适用场景说明 |
| `examples` | 1～5 组范文 |
| `created_at` / `updated_at` | 维护用 |

`key` 规则：非空；仅小写英文字母、数字、点、连字符；长度 1～64。

### 5.2 一组范文

| 字段 | 说明 |
| --- | --- |
| `label` | 可选，维护人备注（如「退款成功」） |
| `requirement_text` | 需求片段，不能为空 |
| `drafts` | 至少 1 条合格 `CaseDraft` |

`CaseDraft` 与 v1 相同：`title`、`preconditions`、`steps`（`action` / `expected` / `test_data` 可空）、`priority`、`tags`、`rationale`。

### 5.3 不变量

- 保存时：至少 1 组范文；每组需求非空；每组至少 1 条通过现有校验的 `CaseDraft`
- 每包最多 5 组范文、合计最多 8 条草稿
- 编辑时把范文删光再保存 → 拒绝，包保持原样
- 无版本号、无软删除、无租户字段

示例（「支付接口」包中的一组）：

- 备注：退款成功
- 需求：用户已支付成功，在订单详情点击退款，退款金额等于实付金额，应退回原支付渠道。
- 用例：标题「订单详情原路退款成功」；前置「订单已支付」；步骤「打开订单 → 点退款 → 确认金额 → 提交」；期望「退款成功、金额一致、原渠道到账」

## 6. 页面

均在 `/debug/`，门控与 v1 相同（`local`/`test` 默认开，`prod` 需 `ENABLE_DEBUG_UI=true`）。

### 6.1 风格包维护

独立页面，不和生成表单混在一起。

- **列表：** 名称、代号、范文组数；入口：新建、编辑、删除
- **新建：** 名称、代号、可选说明；**当场填写至少 1 组范文** 才能保存
- **编辑：** 可改名称、说明、增删改范文；**不能改代号**；保存时仍至少 1 组
- **删除：** 确认后真删
- **表单：** 结构化字段（可少量 JS 增删范文组/步骤），不要让维护人手写 JSON。提交后服务端按 `CaseDraft` 规则校验，错误指出哪一组、哪个字段

### 6.2 生成页

在现有表单增加下拉「用例风格」：

- 选项为已保存包的 `name`（值为 `id`）
- 可空：不选 = 不注入范文
- 不在生成页展开范文全文；核对范文去维护页
- `domain_hint` 保留

导航：生成页与风格包页之间可互相进入。

## 7. 生成链路

选了「支付接口」再点生成：

1. `ingest_requirement`：与 v1 相同（文本/文件二选一、超长超大拒绝）
2. `load_style_context`：按 `style_pack_id` 取包  
   - 未传 id → 跳过，无范文  
   - id 有值但包不存在 → 4xx，不调用模型  
   - 包存在（保存规则已保证有范文）→ 记下包名与组数
3. `generate_cases`：提示词 = 当次需求 + 范文 + 可选 `domain_hint`
4. `validate_cases`：与 v1 相同（失败可带 issues 再生成一次）
5. `persist_run`：轨迹中含风格包步骤，便于回放

提示词约定（真实模型）：

- 范文以明确块注入（包名 + 各组「需求片段 / 合格用例 JSON」）
- `domain_hint` 仍追加在需求后；系统说明中写明：**用例结构、步骤粒度、用词优先模仿范文**
- 需求 + 范文合计超过 `max_text_chars` → 拒绝，文案说明上限

Fake 模型：不读范文，输出仍为固定样例，保证无密钥 CI 稳定。测试用 mock/提示词单测证明范文被拼进 messages。

## 8. API

前缀 `/api/v1`。调试页走同一 application 层。

### 8.1 风格包 CRUD（JSON）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/style-packs` | 列表：`id`、`key`、`name`、`description`、范文组数、`updated_at`；按 `updated_at` 倒序 |
| `POST` | `/style-packs` | 创建；body 含 `key`、`name`、`description?`、`examples` |
| `GET` | `/style-packs/{id}` | 详情（含全部范文） |
| `PUT` | `/style-packs/{id}` | 整包更新：`name`、`description`、`examples`；**不可改 `key`** |
| `DELETE` | `/style-packs/{id}` | 真删；不存在 → 4xx |

创建/更新失败：统一 `issues[]: { code, message, … }`，与 v1 风格一致。code 固定为：

| code | 何时 |
| --- | --- |
| `EMPTY_PACK` | 范文组数为 0 |
| `INVALID_EXAMPLE` | 某组需求空，或 `CaseDraft` 校验失败。`field` 用路径，如 `examples[0].requirement_text`、`examples[1].drafts[0].steps` |
| `PACK_LIMIT` | 超过 5 组或合计超过 8 条草稿 |
| `DUPLICATE_KEY` | `key` 已存在 |
| `INVALID_KEY` | `key` 格式不合法 |
| `PACK_NOT_FOUND` | 更新/删除/生成时 id 不存在 |

### 8.2 生成（既有接口）

`POST /api/v1/case-drafts/generate` 仍为 multipart，增加可选字段 `style_pack_id`。

- 省略或空：v1 行为
- 有值：走第 7 节加载逻辑
- 需求 + 范文超长：沿用 v1 的 `INPUT_TOO_LONG`，message 须写明当前长度、上限，并说明已计入风格包范文

响应 `trace.steps` 增加 `load_style_context`：**未选包则省略该步**（不写 skipped），避免干扰现有回放阅读。选了包则必须出现，summary 含包名与范文组数。

## 9. 持久化

- 表 `style_packs`：`id`（PK）、`key`（unique）、`name`、`description`、`examples`（JSONB）、`created_at`、`updated_at`
- Alembic 迁移；与 `generation_runs` 同库
- `examples` JSON 必须能还原为领域对象。生成加载时若包数据非法 → 4xx（不当成「无范文」静默跳过）。列表接口只返回元数据，不因某包范文损坏而整表失败。
- 并发：后写覆盖，不加锁

## 10. 分层与端口

沿用轻量 DDD：

- `domain/style_pack`：包与范文不变量
- `application`：Style Pack 维护用例；`CaseGenerationService` 增加加载包
- `StylePackRepositoryPort`：list / get / create / update / delete
- `infrastructure`：PostgreSQL 适配；提示词模块增加范文块
- `interfaces`：REST + 调试页

不引入向量库、embedding、独立检索服务。

## 11. 测试策略

| 层级 | 内容 |
| --- | --- |
| domain | 空包拒绝、组数/草稿数上限、`key` 格式、范文 `CaseDraft` 校验 |
| application | 选包则提示词含范文；不选则 messages 无范文块；包不存在不调模型；超长拒绝 |
| persistence | 创建后能读回；删除后 get 为空；`key` 唯一 |
| REST | CRUD 校验与错误码；generate 带/不带 `style_pack_id` |
| 调试页 | 无范文保存失败；列表可见；生成下拉可选；轨迹含包名 |
| Fake / CI | 无密钥全绿；不要求 Fake 输出随包变化 |

## 12. 验收标准

1. 调试站能建/改/删风格包；没有完整范文则存不进去，并指出哪一组哪一字段。
2. 生成页可下拉选包；选中后轨迹可见包名与范文组数。
3. 不选包时，生成行为与 v1 一致。
4. `GET /api/v1/style-packs` 与 generate 的 `style_pack_id` 可用。
5. 删除后再用该 id 生成 → 明确 4xx，未调模型。
6. 无真实密钥时 lint / typecheck / pytest 全绿。

## 13. 后续（不在本轮）

- `cdp-suite`：拉包列表、生成时传 `style_pack_id`
- 鉴权与按系统隔离风格包
- 从已确认入库的用例沉淀进包
- 包数量大、无法点选时，再评估检索（仍作为 Graph 上的 Tool，而不是先做知识库产品）
